# Architecture decisions (append-only)

## D1 — Extend ClickHouse Observe instead of a new plugin (2026-11-17)
v0.10.0 already implements most of Discover on ClickHouse (KQL → SQL with autocomplete, filter pills, field sidebar + stats popover, histogram + breakdown, grid with cell actions, detail drawer, diagnostics). Build Lens and the gaps on top. Spec: `docs/spec/80-blueprint.md`.

## D2 — Frontend-only, queries through grafana-clickhouse-datasource
Keep using `src/data/runQuery.ts` (`getDataSourceSrv().get(uid).query()` with `{rawSql, editorType:'sql', format:1}`). The repo removed its Go backend in 0.4.7. Add a backend only if pattern clustering needs it.

## D3 — Plain React + @grafana/ui, no Scenes migration
Migration cost outweighs the benefit; the app already has its own state + URL sync.

## D4 — Lens rendering
- Bar / line / area (the default auto charts): custom-drawn, generalising `VolumeHistogram.tsx`, because Grafana panels give no one-click "point clicked" callback and the spec requires one-click filter + the multi-dimension "Select filters to apply" chooser.
- Table, Metric/Stat, Pie, Heatmap: `PanelRenderer` (`@grafana/runtime`, public but `@internal`) inside `PanelContextProvider` (`@grafana/ui`, alpha) for table cell filters (`onAddAdHocFilter`) and brush (`onChangeTimeRange`). Isolated in `src/lens/render/` so a Grafana API change touches one place.

## D5 — Deterministic fixture for tests
`default.spec_logs` (`scripts/clickhouse-init/04_spec_fixture.sql`): fixed window 2026-01-01..2026-01-08 UTC, no TTL, 41,520 rows incl. a payments incident on 2026-01-05 09:00–11:00. Tests assert exact counts from `tests/fixture.ts`, never the Kibana numbers in the spec.

## D7 — URL is the shared search context; pinned filters also in session storage (SHARED-STATE)
Every page reads/writes the same URL params (`q, filters, cols, sort, from, to, ds, interval, bd`), like Kibana's `_g`/`_a`, so hand-offs between pages are just links built by `buildAppPageUrl` (`src/state/sharedSearch.ts`). Pinned pills (`FilterPill.pinned`) are also kept in per-tab session storage (`clickhouse-observe.pinnedFilters`), each with the table it was pinned on. The store changes only on explicit transitions (pin, unpin, edit/exclude of a pinned pill, delete of a pinned pill); disable and Clear all are page-only. Pin flags are shown only for conditions in the user's own store (foreign links/saved searches can't plant pins). Pins merge into pages opened without `filters`, loaded saved searches and data view switches — disabled on a view reading a different table. A field breakdown is stored by `FieldModel.id` and resolved once discovery finishes. No React context store was added: LogsExplorer already owns its state and the Lens page will decode the same URL.

## D8 — One autocomplete service for every input (SHARED-AUTOCOMPLETE-01)
`src/autocomplete/service.ts`: `useAutocompleteSources({config, query, timeRange, fieldIndex})` gives `loadValues`/`loadMapKeys` scoped to the time range and the filters on other fields (not the search text, not filters on the field being completed — so typing a new value for a field already in the query offers every value, like Kibana); lookups never reject or throw (failures resolve empty; an unparsable search is dropped from the scope), the scope is compiled once per change, and the cache key distinguishes before/after field discovery. `rankFields(fields, prefix, {allow})` (`src/autocomplete/rankFields.ts`, pure) is the one field ranker: name or display name, prefix-first; the KQL suggestion engine uses it too. New inputs (filter builder, Visualize field pickers, formula editor) must use it — checklist in `docs/spec/30-shared.md`.

## D9 — Dirty state only for the query (DISC-SEARCH-02 / DISC-TIME-02)
Grafana's time picker applies a range immediately (no pending state), so only the KQL bar has a dirty state: when the typed query differs from the committed one, its search icon becomes a primary "Update" button. Matched-term highlighting (`src/sql/kql/highlight.ts`) mirrors the SQL that matched (toSql): fields resolve via `resolveField`, field wildcards expand against discovered fields, an unresolvable `field:value` is a body match on its raw text, wildcard values are one ordered pattern, phrases match on word boundaries; negated/exists/range terms and raw-SQL mode get no highlights. One compiled matcher per column.

## D10 — Action registry (SHARED-ACTION-01)
`src/actions/registry.ts` defines each value/field action once (icon, short tooltip, specific accessible name, compatibility, behaviour): `valueActions(ctx, host, ids?)` → filter for / filter out / copy; `fieldActions` → exists / does not exist. A surface passes an `ActionHost` (`addFilter` omitted = read-only → copy only) and keeps its own layout. Grafana's `IconButton` uses `tooltip` as its accessible name, so icon surfaces use `ActionIconButton` (Tooltip wrapper) to keep names like "Filter for Service: payments". The field list's "filter out rows that have this field" is now a `not_exists` pill (same SQL as the old `= ''`).

## D74 — Rare values: full-range prefix autocomplete + Scan full range (R5-SAMPLING)
User item 15, with both approved changes implemented. Measured on CH 26.3 against `perf_logs_50m`: with `timeout_overflow_mode = 'break'`, an aggregate returns **zero rows** when the time limit fires, with or without GROUP BY. Only `read_overflow_mode = 'break'` returns a partial aggregate. Consequences:
- Autocomplete uses the approved budget (2 s / 20M, both `'break'`). A timed-out lookup returns nothing and only the sampled list shows. On this host a Map-value prefix over all 50M rows took 2–3 s and so returned nothing (`ServiceName` LowCardinality: 1.2 s, found). On a warmer or faster server, or a shorter range, it finds values.
- Stats scan: an explicit click, so its wall clock is **10 s** instead of 2 s. On the perf fixture, reading one Map value column for 20M rows alone takes about 4 s, and a time-limit hit gives no result at all. The row cap stays at 20M. Completeness is decided like this: no row back means the time limit was hit. `scanned ≥ cap`, or an `EXPLAIN ESTIMATE` above the cap, means partial (rows). An estimate within the cap means complete. If the estimate is unavailable (for example, if the Grafana datasource refuses `EXPLAIN`, which I couldn't check without Grafana access), the caption says "completeness unknown". There is no X-ClickHouse-Summary path: the Grafana ClickHouse datasource doesn't expose rows_read in frame meta.
- Exact-but-unbounded aggregates were replaced: top-value counts come from `topK(…, 'counts')`. They are exact while a field has ≤ 10,000 distinct values, and the field is flagged approximate otherwise (or when topK reports an error, or distinct ≥ 65,536 for `uniq`). Numeric distribution: `histogram(20)` re-binned client side into 10 equal-width buckets (approximate). For discrete integers this spreads counts across neighbouring buckets.
- Merge order: full-range matches first (true counts), then sampled-only values. Minimum prefix length is 2 (the brief allowed 1–2), which is lighter on DB load. A KQL wildcard prefix (`pay*`) doesn't trigger a lookup. The prefix lookup reuses the value cache (120 s TTL, key = sampled key with `prefix=<lowercased>`), so `clearValuesCacheForTable` clears it too. Debounce: the KQL bar's existing 250 ms, plus a new 250 ms one on the filter editor's value input.
- Tab scope: the button profiles the current page of fields (≤ 25) and stays on across pages until `Back to sample` or a scope change. It is not persisted in the URL.

Deferred: - Pre-existing, not changed: `suggest.ts` `fieldSqlExpr` falls back to the raw typed field name as the SQL expression for the **sampled** value lookup (`toString(<typed text>)`). The new prefix path refuses such expressions. The sampled path should get the same `isSafeColumnExpr` guard, but that is left to the r5-json agent, who is editing that code.
- The lens/ContextView filter editors get the prefix lookup automatically through the shared service. Lens field pickers don't (they don't list values).
- Real `rows_read` from ClickHouse (X-ClickHouse-Summary) would replace the EXPLAIN-based estimate. It needs datasource support.
- A smarter time budget for the stats scan (a progressive/sliced scan that keeps partial results when the time limit is hit).

## D73 — JSON fields end to end + Map/JSON field markers (R5-JSON)
Kibana-like behaviour where a product choice was needed: an array path matches when any element matches (Elasticsearch multi-value semantics); a value query on a whole object (JSON column) matches nothing, `Payload:*` is "has any path"; a field's type tooltip is shown on hover of its label (the sidebar row keeps its `title` = SQL expression, which existing specs and the row semantics rely on). Dynamic-path types: sampled from the first 1,000 rows read (no ORDER BY, so a few granules) rather than the newest rows, which would read the JSON column of the whole range on servers without lazy materialization; a path with several types, a date / decimal / other type, or not seen in the sample stays a bare `Dynamic` string field (stringified everywhere), so no query can hit the Dynamic restrictions. JSON array paths are type `array` and so, like other containers, not offered in Visualize. The typed expression replaces the bare one in `FieldModel.sqlExpr`; a filter / KQL / URL column using the bare dotted name still resolves to it through the display-name lookup. Root causes: (1) dynamic paths were published as bare `Dynamic` expressions typed 'string', which ClickHouse refuses in GROUP BY / numeric aggregates and casts NULL→0 in `toFloat64`; (2) the KQL bar offered the JSON column itself as a terminal field (`Payload : value` compares a whole object), not a drill-down; (3) the document panel treated any discovery error, including one JSON column's path-lookup failure, as fatal.

Deferred: - Saved Visualize charts / URLs that reference a dynamic path by its old bare expression (`Payload.x`) are dropped by Visualize's field check now that the field reads `Payload.x.:Int64` (Discover filters and KQL still resolve the bare name). A remap in `sanitizeLens` would keep them.
- The `spec_logs` fixture only has the declared `Payload.user.id` (always 0), so e2e covers declared paths only; dynamic-path behaviour is covered by jest and by running the SQL against `otel_logs`. Seeding a few dynamic paths into `04_spec_fixture.sql` would let e2e cover them (fixture change needs a reseed).
- Histogram breakdown by a typed JSON path counts rows without the path under "Other".
- A JSON path with several observed types (e.g. Int64 + String) stays a text field.

## D69 — Stuck Discover tab no longer blocks other tabs (R5-TABS)
R5-TABS (user item 4: "if the first tab in discover is stuck then all others are as well … same with visualize"). Only the active Discover tab is mounted (unchanged), so "inactive tabs must not query or hold results" already held; the gap was that the unmounted tab's in-flight requests kept running. `useAbortOnUnmount` (`src/data/abortOnUnmount.ts`) aborts the latest list / histogram controllers and bumps their run ids when `LogsExplorer` unmounts; `useFieldDiscovery` bumps its run id on unmount so a gone page starts no Map-key samples. Shared, deduped metadata reads (system.columns, JSON paths, skip indexes) are deliberately not aborted: another tab may be waiting on the same promise and they are cheap. Visualize already aborted its chart / layer queries on unmount. Memory was not the cause: one tab's rows are held at a time; the tab list stores URL params only. Not changed: ClickHouse keeps executing an abandoned query (HTTP protocol; probed `cancel_http_readonly_queries_on_client_close` as a query setting and a URL parameter, neither stopped a running `sleepEachRow` query).

Deferred: - Server-side cancellation of abandoned queries (`KILL QUERY` by a tagged `query_id` / `log_comment`; needs the KILL grant).
- On-demand popover queries (field top values, Map keys) and "Search entire time range" take no abort signal; they are LIMIT-sampled and short.

## D68 — Visualize round-3 fixes: percentile rank, pie labels, faster open (R4-VIZ)
R4-VIZ (round 3 Visualize rows 8, 18, 19, 20, 22, 23).

Percentile rank follows Kibana 9.5's `percentile_rank` operation (read from its Lens bundle): `operationParams: value` (number, default 0), number fields only, filterable / shiftable, allowed as a reference (inner metric) — so it is in `BASE_OPS`, except Cumulative sum (Count / Sum only, unchanged). Kibana's `aggSinglePercentileRank` returns the ES percentage / 100 with the serialized format `percent`; we return the same 0–1 share and default the display to percent with two decimals through `formatOf(metric)` (the metric's own format wins; a calculation over a percentile rank also defaults to percent), applied in every renderer and in saved panels (`percentunit`). The formula result keeps the number format (Kibana's formula column has no per-function default). The SQL is the exact share (`avgOrNull(toFloat64(x <= v))`, NULLs skipped, no values → empty), not ES's TDigest estimate: on the fixture `percentile_rank(SeverityNumber, value=9)` is 77.67 % here and 66.25 % in Elasticsearch, whose TDigest interpolates across the many equal values (9.60 % are < 9, 77.67 % are ≤ 9); Kibana's own docs define it as "the percentage of values which are below a certain value" with "greater than or equal to 95 % of the observed values" — the exact ≤ share. `rankValue` lives in `calc.ts` with the other calculation constants (state.ts re-exports it) to keep formula.ts free of a state.ts import cycle.

Pie / Donut: Grafana's piechart has one panel-wide label switch, whole-number percents and no collision handling, so the slices are drawn by `render/PieChart.tsx` like the XY charts and the heat map. Placement: try the label inside the slice (exact box-in-sector test, a few radii for a pie, the ring's middle for a donut; one line, then name / percent on two lines), else outside left / right of the mid-angle with an elbow leader line; outside labels are spread per side top to bottom (forward then backward pass) and, when the height cannot hold them all, the smallest slices lose their label (legend and tooltip keep the numbers). The pie shrinks to leave room for outside labels. The old Grafana-panel path (`pieSpec`, `pieDisplayLabels`) stays for multi-series pies and is what `panelSpec` still describes. Click on a slice uses the existing filter chooser (`onSelect`, x index = slice).

Fresh open: the brief asks for an empty workspace on a fresh open while a reload keeps the chart. A reload keeps the URL (`lens`), so the session draft's only remaining effect was the behaviour being removed; it is deleted (`src/lens/draft.ts`, `visualizeEntry`'s step 4, the save effect) rather than kept as dead storage. A stale `clickhouse-observe.lensDraft` entry in a tab's session storage is simply never read.

Open performance: on perf-50m the 7 queries were `system.columns`, `system.data_skipping_indices`, `distinctJSONPaths(Payload)`, three map-key samples and the chart; the chart waited for columns → skip indexes → JSON paths (three serial round trips; each query is 8–80 ms in ClickHouse, the rest is the Grafana round trip). Now the chart waits for the columns only (`lensFieldsPending`: columns published and, while discovery is still running, every field of the chart already known — `sanitizeLens` would not drop anything), Visualize does not request skip indexes (its search compile never used them: `buildFieldIndex(fields)` without text indexes), and other pages fetch them concurrently with the columns (shared in-flight promise per table). Map-key samples still run (the field list needs them), after the columns and in parallel with the chart. Not measured here (no browser runs): expected about two round trips less before the chart; the remaining ~3 s is Grafana's own boot.

Search suggestions: `commit()` / `onClear()` already closed the list, but the 250 ms debounced value fetch (and a Map-key fetch) of the last keystroke was still allowed to reopen it. Both now bump the request sequence and clear the debounce (`cancelPendingSuggestions`).

Metric tiles: `grid-auto-rows: minmax(110px, 140px)` with the grid's definite height lets the rows grow to 140 px only within the free space, so three rows fit a 428 px area; more rows than fit at 110 px scroll as before.

Deferred: - Saved dashboard pie / donut panels still use Grafana's piechart (whole-number labels, no collision handling); only Visualize draws its own.
- Kibana rotates a thin slice's label along the slice; here it goes outside with a leader line instead.
- Pie legend position / visibility from Style → Legend (XY only today); the pie legend is always shown (right, or below under 420 px).
- Map-key samples: three queries (one per Map column) are kept; merging them into one sample query would save two more requests but changes the shared, per-column cached key sampler.
- Lens's KQL compile does not use the table's text skip indexes (unchanged; Discover does).

## D65 — Data views without a time field (NO-TIME)
A data view may have no time field (timeless reference tables). ## D64 — Visualize chart types: bar horizontal, donut, heat map, gauge (R3-CHARTS)
R3-CHARTS (Kibana comparison round 2, #15). ## D63 — Visualize metric functions and calculations (R3-FUNCTIONS)
LENS-CALC-01 (Kibana comparison round 2, #15). Semantics mirror Kibana 9.5's datatable functions, read from its bundles (`cumulativeSumFn`, `derivativeFn`, `movingAverageFn`, `counterRateFn`, `overallMetricFn`): cumulative sum carries the running total over empty values; differences is empty when the current or previous value is empty (a gap breaks the chain); moving average is the mean of the last *window* non-empty values before the current one (current excluded, empty values skipped, empty when the current value is empty); counter rate is the difference, or the new value when it dropped (reset), divided by the bucket length (Kibana's mandatory time scale, default per second; partial edge buckets are not scaled down); overall_* ignore empty values and are per series, where the series is defined by the date histogram / intervals and split by top values / filters, over all rows when neither exists (Kibana's docs). Cumulative sum's inner metric is Count or Sum only (Kibana's restriction). Time-series functions require a date histogram (Kibana: "To use this function, you need to configure a date histogram dimension as well"); overall_* do not. Formula `counter_rate` is per bucket ("uses the current interval when used in Formula"); converting a quick Counter rate to a formula keeps per second through Normalize by unit. Computation is SQL window functions over the grouped query rather than client-side, so Visualize, the Inspector's rows and saved dashboard panels show the same numbers; gap filling moves into SQL (WITH FILL) for these charts because the calculations must see empty buckets (count / sum / unique = 0, other aggregates empty via `-OrNull`). Drop partial intervals filters before the window in app mode (saved panels ignore it, as before). Ranking top values by a calculation is not offered (no single value per series), except Cumulative sum, whose total is its inner metric's total. Window functions cannot be nested or used inside an aggregation. Last value skips documents without the field (Kibana's `exists` filter) and is numeric only.

Deferred: - Last value of string / date fields (Table / Metric only) — numeric only for now.
- Counter rate scaling of partial edge buckets (Kibana scales the first / last bucket by the part the time range covers).
- Percentile rank, and Kibana's `normalize_by_unit()` / `interval()` / `time_range()` formula functions.
- Drop partial intervals in saved panels (ignored there, as before this change).
- A per-dimension error marker in the dimension list (the chart area explains the error).
- `src/lens/render/LensChart.tsx`: one line — a missing time bucket is 0 only for count series (PanelRenderer frames), so calculation gaps are not drawn as 0.

## D61 — Saved searches: tab title, id in the URL, optional time, own folder (R2-SAVED)
R2-SAVED. Supersedes the folder deferral in D50. Folder: documented API is `/apis/folder.grafana.app/v1/namespaces/{namespace}/folders` (Grafana 12+, the plugin requires 13; the legacy `/api/folders` is not in the current docs). The folder has a fixed uid (`observe-saved-searches`, the `metadata.name`), so it is found with GET by uid (no folder listing right needed), created with POST when missing (409 counts as found), the namespace is `config.namespace`. Any failure (read, create, or writing the dashboard into it) falls back to General, so users who cannot create folders behave exactly as before; only a success is cached. Listing is unchanged (tag search across folders). `ss` URL param: the id is validated against the generated shape (`ss_<ms>_<random>`) because the URL is untrusted. A link with `ss` and no query of its own (no q/filters/cols/sort) reopens the saved search (time from the link if present, else the stored one); a link with a query is trusted as is, and the lookup (title search by id, one dashboard read) only names the tab. The id is cleared by comparing search, filters (ignoring ids), column ids and sort to a baseline taken from the first state after the open; the time range is not part of it. ## D52 — Performance: ClickHouse dev memory config that recovers, chart result reuse, windowed surrounding documents, histogram axis numbers (PERF-QUERIES)
**#1 ClickHouse memory (config only; the running container keeps its hand-set 3.5 GiB / 4 GiB until recreated).** Research basis (ClickHouse 26.x behaviour from the docs and source as I know them; not re-verified against the 26.3 image, docker was off limits): the server-wide memory tracker compares `max_server_memory_usage` with the larger of its own tracked allocations and the process RSS, refreshed by the asynchronous-metrics thread, so memory that is resident but no longer tracked still counts. jemalloc keeps freed pages as dirty / muzzy pages and returns them after `dirty_decay_ms` / `muzzy_decay_ms` (image default 5 s, background thread on), so RSS lags tracked memory and an interrupted heavy query leaves it above the cap; with a 2 GiB cap and a 2.28 GiB RSS every allocation, including the healthcheck's, was refused. `mmap_cache_size` is a file count (256), not bytes, and the uncompressed cache is 0, so neither explains the drift; the userspace page cache is off by default; the mark / index caches are already capped (about 0.45 GiB together). `max_server_memory_usage_to_ram_ratio` (0.9) only lowers the cap when the cap is 0 or above ratio times the RAM the server sees (cgroup limit), so it is pinned explicitly. Chosen: steady RSS (about 1 GB, 2.3 GiB seen after a reaped run) < cap 3.5 GiB < `mem_limit` 4 GiB, so drift cannot cross the cap and the kernel OOM line sits above it; 0.5 GiB headroom for untracked memory (stacks, jemalloc metadata). `MALLOC_CONF=background_thread:true,dirty_decay_ms:1000,muzzy_decay_ms:1000` (jemalloc merges it over the image's built-in options) makes idle RSS track tracked memory faster. Safety net: Docker never restarts an `unhealthy` container, so `restart: unless-stopped` alone would not help; the healthcheck exits with the client's code and, only on 241 (MEMORY_LIMIT_EXCEEDED), also runs `kill 1`, which ends the server and lets the restart policy bring it back (data is on the volume; startup failures, refused connections and other errors only report unhealthy; `start_period: 30s`). ## D34 — Metric advanced options (Filter by, Time shift, Reduced time range, Normalize) and appearance (LENS-DIM-02-ADV)
LENS-DIM-02-ADV (PLAN 16g).

**Options are stored on `MetricDim`, validated on decode.** The options live on `MetricDim` (`MetricOptions` in `src/lens/metricOptions.ts`). `decodeLens` now rebuilds every metric from known keys only: before this, quick-function metrics passed through with any extra keys. `cleanMetricOptions` validates each option:
- shift and reduced range must parse as `<1–99999><unit>` within 10 years, and are stored canonical;
- the colour must be `#rrggbb`;
- enums are checked, and a custom pattern must match the numeral grammar.

**SQL is printed only from parsed values.** SQL uses only the parsed integer and a fixed unit keyword (`chInterval`), never the text. Filter by goes through `kqlToSql`, which escapes values and resolves fields. In dashboard mode a `$` in a Filter by becomes `\x24`, as for formula `kql=`.

**Time shift is one query (ARRAY JOIN), not one query per shift.**
- `compileLens` swaps the standard time condition (and its coarse partition bound) for two things: a prefilter that ORs the main window with each shifted window, and an exact check on the shifted time.
- Date buckets use the shifted time. In dashboard mode that is the explicit `toStartOfInterval(…, $__interval_s)` form, not `$__timeInterval`.
- Each metric's aggregate is conditioned on `__s = k`. Formula metrics get `__s = 0` through the new `FormulaSqlContext.rowCond`, which every aggregate in the formula ANDs with its own `kql=`.
- Ranking by count uses `countIf(__s = 0)`.
- A top-values CTE still ranks over the unshifted window.

**Filter by, shift and reduced range don't apply to formulas.** Formulas have their own `kql=` argument, and `shift=` remains deferred. The editor points users to the arguments.

**A metric's Filter by also applies when a top-values bucket ranks by that metric.**

**Appearance:**
- XY charts are custom SVG, so `XyChart` applies the format, the colour (only without a breakdown) and a right axis. Stacked charts keep one axis, since stacks are per axis in Kibana and mixing them is confusing.
- PanelRenderer charts and exported panels use one shared mapping, `withMetricAppearance`. With one metric the options go in field defaults; with several, each metric gets a `byRegexp` override on its label.

**Function changes keep the options.** `withOp` and `formulaMetric` carry them over, so a switch never loses them.

Deferred: - Time shift and reduced range inside formulas (`shift=` / `reducedTimeRange=` arguments).
- Value format on the date histogram axis and in Discover-style number fields.
- Right axis on stacked charts.
- A colour picker with Grafana's palette (a native colour input is used).

## D27 — Security: sanitize URL / saved-search columns and sort (URL-COLS)
SEC-URL-COLS. Anything restored from a URL or storage is data, not SQL. ## D26 — Surrounding documents (DISC-DOC-02)
DISC-DOC-02 (surrounding documents). ClickHouse tables have no document id, so a document is identified by its sort values, Kibana-style: (timestamp in epoch nanoseconds, row id), the row id being `cityHash64` of the timestamp and the mapped body / severity / trace id / service columns, the same fields `logRowKey` compares; rows equal on all of them are indistinguishable everywhere in the app anyway (the fixture has none). Both values are 64-bit, so queries return them with `toString` and they travel as decimal strings (a JS number would round them). The two `search_after` searches are tuple comparisons, `(ts, id) > anchor ORDER BY ts, id ASC` and `(ts, id) < anchor ORDER BY ts, id DESC`, each `LIMIT size`, plus a plain `ts >= / <= anchor` bound and the coarse partition bound so ClickHouse can prune parts. The anchor itself is a third exact-match query, so "anchor not found" (deleted, or excluded by a re-enabled filter) gets its own message. "Load N" raises the requested size and re-runs only that side. Opening from Discover first resolves the grid row to its anchor with one point lookup (same match as the detail query); rows on the context page already carry their anchor values (`__ctxNs`, `__ctxId`), so re-anchoring there needs no lookup. The URL carries the anchor in the path (`<ns>_<id>`) and the shared `filters` / `cols` / `from` / `to` plus `ret` (Discover's query string, for the breadcrumb). Filters arrive disabled; disabling never touches the pin store, so pinned filters are still pinned and enabled back in Discover. The time range is carried only for field discovery and the way back; the neighbour queries ignore it. Not done: "View single document" permalink (the context URL already identifies one document), row-level entry from the grid (the detail panel is the spec's entry point), and a hard cap on how far back the older search may scan (on a table whose sort key does not start with the timestamp an older search on a sparse filter can read many parts; `max_execution_time` still applies).

## D24 — Top values editor: rank by / direction, Other, missing, include / exclude with regex (LENS-DIM-04)
LENS-DIM-04: top values options live on `TermsDim` as optional fields (`rankBy` count|alpha|metric, `rankMetric` metric id, `rankDir`, `other`, `missing`, `include`, `exclude`, `regex`); defaults are omitted so existing URLs and default SQL are byte-identical. A bucket without Other / missing compiles exactly as before. With Other and/or missing on, a row-kind column `kN` (0 value, 1 Other, 2 missing) is returned beside it and the value column is empty for synthetic rows, so a real value spelled "Other" or "(missing)" can never merge with the synthetic bucket (the shaper keys synthetic buckets with a U+0000 prefix and shows a colliding real value as "Other (value)"; its click filter still uses the real value). "(missing)" is an extra bucket outside the top N and NULL never takes a ranking slot. Other keeps every eligible row. For Map accessors the missing test is `mapContains(map, key)` (an absent key reads as '' otherwise); for a non-Nullable column there is no "missing", an empty string stays a value. The outer ORDER BY follows the rank (alphabetical by value, custom metric by its column, count by `count()` or `m0`) in the chosen direction, with Other and (missing) always last. Every user string goes through `quoteString`, and `$` is written as `\x24` so the datasource macro expander in saved panels never sees `$__...` text. Regular expressions are validated (`regexError`): unbalanced parentheses or brackets, a trailing backslash (both could break out of the `^(?:p)$` wrapper), lookaround, back-references and invalid syntax are rejected (character classes are parsed as RE2 parses them: a `]` right after `[` or `[^` is a literal, `[:alpha:]` is one item) in the editor with a message under the field and the text is kept; the compiler also skips such patterns (URL input is untrusted) and an include list with no usable pattern matches nothing. Lists over 50 values or 200 characters per value are reported, not silently cut (URL input is still capped). Synthetic rows are not clickable (no filter), and "Custom metric" is disabled without a metric; removing the rank metric resets the stored rank to count. Labels follow the rank: "Top/Bottom N values of X" (count), "First/Last N values of X" (alphabetical), "... by <metric>" (custom). Not implemented: multi-field terms, "Aggregate by this dimension first", Rarity and Significance ranking (ascending count covers rarity), accuracy mode (ClickHouse aggregates are exact, no shard_size).

## D23 — Filter builder: range operators, per-type operators, preview (DISC-FILTER-02)
DISC-FILTER-02 (filter builder). Range filters are four new pill ops rather than a generic "range" object, so they plug into the existing pill pipeline unchanged (URL `filters`, saved searches, pin, negate, disable). Bounds live in `values` like one-of, compared inclusively (`BETWEEN`). Pill range ops are not used by matched-term highlighting (no text to highlight). ## S1 — Identifier quoting mirrors the ClickHouse lexer (security, 0.26.1)
Every identifier part goes through `quoteIdentPart` (backslash escaped, then `"` doubled); `QUOTED_IDENT` (the pass-through check for Map accessors / dotted paths) accepts exactly what ClickHouse lexes as one quoted identifier (`[^"\]`, `""`, `\.`). A pre-existing hole: `"x\""` used to end at the first lone `"`, so a URL field name could inject SQL (verified on the dev ClickHouse; regression tests in `src/sql/__tests__/identifier_quoting.test.ts`). `tableRef` uses the same quoting.

## D21 — Saving a Lens chart (LENS-SAVE-01)
A saved chart is a core Grafana panel running the compiled Lens SQL on the ClickHouse datasource (`src/lens/panelExport.ts`). Dashboard mode compiles date buckets with `$__timeInterval(col)` (expression fields containing `(),` use `toStartOfInterval(toDateTime(expr), INTERVAL $__interval_s second)` so the macro's argument parsing can't be confused), so the panel follows the dashboard time picker and resolution; filters keep `$__fromTime/$__toTime`. Long rows are reshaped by standard transformations: time + split → `partitionByValues` + `prepareTimeSeries`; category + split → `groupingToMatrix`; otherwise `organize` renames aliases to the Lens labels. Panel types: XY over time → timeseries (bars/lines, stacking normal/percent/none), XY over categories → barchart, Metric → stat, Pie → piechart, Table → table. "Add to library" creates the library panel first and the dashboard references it (`libraryPanel {uid,name}`), so one save never leaves a dashboard pointing at a missing panel. A new dashboard gets the chart's time range (relative strings kept); an existing one is appended below, saved in its folder with overwrite. Unsaved charts survive a refresh via the URL and a per-tab sessionStorage draft (`src/lens/draft.ts`), restored only when the page opens without `lens`; the draft goes through `decodeLens` + `sanitizeLens` like the URL. Security review: no findings.

## D20 — Discover ↔ Lens hand-off is a URL (LENS-INTERACT-02, DISC-CHART-03)
Hand-offs are links built by `src/lens/handoff.ts`: the shared context (q, filters, time, ds) plus `lens` (to Visualize) or `cols` (to Discover). Visualize from the field popover builds exactly what adding that field first would (`addField(EMPTY, field)`), so both entry points agree. Edit visualization = Records → Bar stacked over the time field, plus the histogram's breakdown (field or severity column) as a terms bucket. Explore in Discover opens a new tab (spec) and carries only top-values bucket fields as columns; Discover's columns, sort and interval do not travel to Lens. The receiving page re-validates everything (`sanitizeLens`, Discover's column decode). Discover gets the view's default columns plus the new bucket fields (a grid of only bucket fields would hide time and message). The new tab's href goes through `locationUtil.assureBaseUrl` (no Grafana router there, so sub-path installs need it). Known limits: pins live in per-tab session storage and are not copied to the new tab (the filters themselves travel, unpinned); Edit visualization splits severity by raw top-9 values of the severity column, like the histogram's own query, but without its colour mapping.

## D19 — Click-to-filter on Lens charts (LENS-INTERACT-01)
Bar, line and area are drawn by `src/lens/render/XyChart.tsx` (SVG), not PanelRenderer, because Grafana panels give no one-click point callback (blueprint decision). Marks are keyboard-focusable buttons. A click builds candidate filters from the clicked X (top value → `=` pill; date bucket → time range) and the series' breakdown value; one candidate is applied at once, several open "Select filters to apply" with all ticked. Pills are built through the action registry (`filterFor` / `filterOut`), added with `addFilterPill` (dedupe) and written to the shared URL `filters`, so Discover sees them. Legend items toggle visibility; ⋮ offers Filter for / Filter out on the breakdown value. Dragging across a time X sets the time range. Metric / Table / Pie stay on PanelRenderer (table cell actions later). Review fixes: filters + time from one chooser Apply go into ONE URL update (react-router's setSearchParams updater sees render-time params, so two calls lose the first); empty time buckets are filled so the axis is linear (brush/bars match real time); a missing point is a gap except for counts (0); negative values stack downwards with a scale below 0; NULL never takes a top-N slot (it can't match the outer GLOBAL IN); legend menu keyed by series name and only for a top-values breakdown; brush listeners removed on unmount; the svg is role=group so its buttons stay accessible.

## D18 — Dimension editor (LENS-DIM-01/02)
The editor replaces the dimension groups (and the type switcher) while open, titled by the group it was opened from. Quick functions: Average, Count, Maximum, Median, Minimum, Percentile, Sum, Unique count (counter rate, cumulative sum, differences, moving average, last value, std dev, percentile rank come with formula/advanced work). Changing function keeps the field when compatible (numbers for numeric aggregates, any scalar for unique count), else the first compatible field. Every dimension can carry a user `name`; blank = automatic label. Percentile is a number clamped 1–99 and validated on URL decode (it reaches SQL as a formatted number, never as text). "+ Add" slots: metric groups add Count of records and open the editor; bucket groups add Top values on the first field and open the editor. Review fixes: number boxes (Percentile, Number of values) keep a free-typed draft and apply the clamped value on blur/Enter; a new bucket never repeats a field already used; slots accept dropped fields (metric groups: number → median, other → unique count, Records → count) and are disabled when nothing fits; renaming doesn't re-run the query (`queryShape` drops names from the query key); the editor's group is looked up from the current state each render. Moving dimensions between groups by drag is still deferred.

## D16 — Lens model, compiler and rendering (LENS-AUTO-01 / LENS-SUGG-01)
LensState keeps one layer as ordered `buckets` (date histogram / top values) and `metrics`; chart roles are read positionally (XY: X, Breakdown; Table: Rows; Metric: Break down by; Pie: Slice by), so `switchChart` implements the LENS-TYPE-01 remapping by re-capping lists — dimension ids, labels and later formats survive. Suggestions follow the spec table and are unit fixtures. SQL: date histogram uses the Discover auto interval (~60 buckets), top values are restricted with `GLOBAL IN` a ranked CTE (no "Other" yet), number fields default to median (`quantile(0.5)`), non-numeric fields are cast for numeric aggregates. Results render through Grafana panels via one adapter (`src/lens/render/LensChart.tsx`); only chart types with a core panel are offered (line, area, bar, metric, table, pie). Lens state lives in the URL (`lens`); search/filters/time are the shared Discover params. The page is lazy-loaded.

**Security (security-review on PR 12):** the `lens` param is untrusted. `sanitizeLens` keeps only dimensions on discovered fields (plus the time column) and nothing runs until discovery finishes; `compileLens` also passes every field through `quoteIdentifier` (only well-formed Map accessors / dotted paths pass unquoted). Regression tests in `src/lens/__tests__/compile.test.ts` and e2e `lens-auto-01.spec.ts`. Review fixes: adding a field keeps the user's chart type; removing a line's time axis re-picks the chart; flip only for category × category; pie holds one slice dimension; duplicate metric labels get "(2)"; date buckets return as epoch ms (no timezone guessing); superseded queries are aborted.

## D15 — Document flyout (DISC-DOC-01)

## D14 — Histogram bucket actions (DISC-CHART-01)
Right-click on a bar opens a pinned popover (`BucketActionsPopover`): "Filter by time" zooms to that bucket, "Filter N selected series" adds one pill — `=` for one series, `one_of` for several (separate `=` pills would AND to nothing). ## D13 — Field list groups (DISC-SIDEBAR-01)
Groups: Selected, Popular, Available. Popular = up to 5 fields used from the list (added as a column or filtered on), counted per viewer and table in localStorage (`src/state/fieldUsage.ts`); they're listed once (not again under Available). Only fields that are rows of the list count (drilled Map keys don't), ineligible ids are dropped before the top-5 cut, and in-memory counts keep working when storage is blocked. Counts are per table (the source config has no data-view id). The type filter resets when the table changes. No Empty group: telling empty from available needs a per-field existence query, which the perf plan removed; revisit with SHARED-PERF-01. No Meta group (ClickHouse has no `_id`/`_index`). Type filter counts follow the name search.

## D12 — Grid keyboard model and Expand (DISC-TABLE-01/02)
Roving focus is per cell (`data-cell="row:col"`, `aria-selected`), not per row. Enter opens the cell's Expand popover as the spec says; Shift+Enter opens the row's detail drawer (what Enter used to do; also on the "Open detail" button). A mouse click focuses the clicked cell, but the action bar follows the keyboard cursor only while the keyboard drives the grid. PgUp/PgDn are taken only when the page really changes (one step at a time). Expand pretty-prints JSON text by re-indenting it, never re-serializing (UInt64 IDs keep every digit). Expand is a registry value action (`expand`, shown only when the host provides it), so its popover's buttons are the same Filter for / Filter out / Copy as everywhere. Display options (density, body lines; default Normal / 3) are a per-viewer convenience in localStorage, not URL state. Summary column and sample size are deferred: the OTel Body column already plays the summary role and the grid pages on demand.

## D11 — Field stats popover sampling (DISC-SIDEBAR-02)
The popover samples the 5,000 most recent matching rows (`STATS_SAMPLE_SIZE`); autocomplete keeps 500 (`DEFAULT_SAMPLE_SIZE`) to stay light; the shared cache key includes the sample size. Numeric fields get min / median / max + 10 equal-width buckets in one query (`buildNumericStatsQuery`) that reads the sample once (`groupArray` + `arrayCount`), so summary and buckets describe the same rows even with timestamp ties, and the division is guarded inside `floor` (constant fields can't hit NaN). Which fields can split the histogram is one predicate, `isBreakdownField` (scalars, not Map/JSON/Tuple/Array), shared by the toolbar picker and the popover. The fixture's `SeverityNumber` uses OTel severity numbers so numeric stats are testable. Breakdown and Visualize are registry field actions shown only when the host provides them.
