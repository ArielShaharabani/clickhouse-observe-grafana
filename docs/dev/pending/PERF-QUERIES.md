# PERF-QUERIES pending notes

**This change touches SQL generation** (`src/sql/queryBuilder.ts`): `buildSurroundingDocsQuery` takes an optional `windowSec` and, for newer / older neighbours, adds `Timestamp <= anchor + INTERVAL w SECOND` (newer) or `Timestamp >= anchor - INTERVAL w SECOND` (older) plus the same bound, widened by 1 s, on the partition column when mapped. `w` is inlined only when it is a positive integer (`Number.isInteger(w) && w > 0`); it comes from the code constant `CONTEXT_WINDOWS_SEC`, never from user input. Anchors are unchanged (still validated by `isContextAnchor`). No other SQL changed; `src/lens/compile.ts` is untouched (item 4 not implemented). Also changed, dev only: `docker-compose.yaml`, `scripts/clickhouse-config/low-memory.xml`.

## CHANGELOG

### Changed
- **Dev ClickHouse no longer locks itself out (#1).** Server cap 2 GiB to 3.5 GiB, container limit 3 GiB to 4 GiB, `restart: unless-stopped`, jemalloc returns freed pages after 1 s, and the healthcheck restarts the container when the server answers MEMORY_LIMIT_EXCEEDED.
- **Chart-type switches reuse the last result (#5).** Bar to Line to Area no longer re-runs identical SQL: the rows of the last 8 distinct queries are kept for 60 s (keyed by datasource, compiled SQL and time range). A new Refresh button next to the time picker always re-runs.
- **Surrounding documents search a narrow window first (#6).** Neighbours are looked up within 1 min of the anchor and the window widens (1 h, 1 d, 30 d, unbounded) only while fewer rows than requested come back, so large tables read a few granules instead of every part.
- **Discover histogram value axis uses the Visualize number format (#9).** `1,000`, `25,000`, `50M`, `1.5B` instead of `1 Mil`.

## Decision

**#1 ClickHouse memory (config only; the running container keeps its hand-set 3.5 GiB / 4 GiB until recreated).** Research basis (ClickHouse 26.x behaviour from the docs and source as I know them; not re-verified against the 26.3 image, docker was off limits): the server-wide memory tracker compares `max_server_memory_usage` with the larger of its own tracked allocations and the process RSS, refreshed by the asynchronous-metrics thread, so memory that is resident but no longer tracked still counts. jemalloc keeps freed pages as dirty / muzzy pages and returns them after `dirty_decay_ms` / `muzzy_decay_ms` (image default 5 s, background thread on), so RSS lags tracked memory and an interrupted heavy query leaves it above the cap; with a 2 GiB cap and a 2.28 GiB RSS every allocation, including the healthcheck's, was refused. `mmap_cache_size` is a file count (256), not bytes, and the uncompressed cache is 0, so neither explains the drift; the userspace page cache is off by default; the mark / index caches are already capped (about 0.45 GiB together). `max_server_memory_usage_to_ram_ratio` (0.9) only lowers the cap when the cap is 0 or above ratio times the RAM the server sees (cgroup limit), so it is pinned explicitly. Chosen: steady RSS (about 1 GB, 2.3 GiB seen after a reaped run) < cap 3.5 GiB < `mem_limit` 4 GiB, so drift cannot cross the cap and the kernel OOM line sits above it; 0.5 GiB headroom for untracked memory (stacks, jemalloc metadata). `MALLOC_CONF=background_thread:true,dirty_decay_ms:1000,muzzy_decay_ms:1000` (jemalloc merges it over the image's built-in options) makes idle RSS track tracked memory faster. Safety net: Docker never restarts an `unhealthy` container, so `restart: unless-stopped` alone would not help; the healthcheck exits with the client's code and, only on 241 (MEMORY_LIMIT_EXCEEDED), also runs `kill 1`, which ends the server and lets the restart policy bring it back (data is on the volume; startup failures, refused connections and other errors only report unhealthy; `start_period: 30s`). Unverified, to check when the stack is next recreated: the client really exits 241 for that error, and `kill 1` is permitted for the healthcheck user.

`docs/dev/CONTEXT.md` (not edited by this agent, per the rules) should replace its "ClickHouse gotcha" bullet and the `.e2e-lock` restart wording with: the cap is now 3.5 GiB under a 4 GiB container limit with auto-restart on MEMORY_LIMIT_EXCEEDED; a manual `docker restart clickhouse-observe-grafana-dev-clickhouse-1` is only needed for a container that predates this compose file (recreate it with `docker compose up -d clickhouse`).

**#5.** The cache holds raw rows, not shaped data, so Bar / Line / Area (same SQL, different shaping) share an entry while anything that changes the SQL (dimensions, metrics, filters, search, time range, datasource) misses. Module-level LRU (`src/lens/resultCache.ts`, 8 entries, 60 s TTL), so it also survives leaving and re-entering Visualize within the minute. An absolute time range keeps the same key; a relative one that resolves to a new `now` is a new key, so stale data is not served for it. Refresh (a nonce in the effect deps) skips the lookup and overwrites the entry. Errors are never cached. The "keep drawing the previous chart while the new one loads" path is unchanged.

**#6.** The old query bounded only one side of the anchor (`>=` for newer), so ClickHouse could still scan every later part. A two-sided window on both the time column and the partition column lets it prune parts and granules. Widening is client side in `useSurrounding` (`src/pages/ContextView.tsx`): it stops at the first window that returns the requested count, so sparse tables cost up to five cheap queries, dense ones one. Order and the tuple cut are unchanged, so results equal the unbounded query's. The anchor point lookup is unchanged. Not measured at 50M rows (no docker); expected cost is proportional to the window, not the table.

**#8 not implemented.** A single pass (aggregate by date x term once, rank in an outer query or `WITH TOTALS`) is not correct in general: the top-N is ranked on the whole filtered set by the chosen metric (count, or any metric: unique count, average, percentiles, last value), and the Other bucket must re-aggregate every non-top term per date bucket. That is only possible from (date, term) partials for additive metrics (count, sum, min, max); averages, unique counts and percentiles would need aggregate-state columns (`-State` / `-Merge`) and change the row shapes that `shapeLensRows`, WITH FILL and the legend ordering depend on. `WITH TOTALS` yields one grand total row, not a per-term global rank, so it cannot pick the top N. A single pass also groups by date x term for all terms at once (memory grows with term cardinality x buckets), which the CTE form avoids by restricting the main scan to N terms when Other is off. The CTE scan reads one column of the same table, so it is mostly page-cache warm for the second pass. A future additive-only fast path (count / sum) is possible but doubles the compile branches for a saving of at most the CTE time; deferred.

**#9.** The formatter moved to `src/utils/axisNumber.ts` (re-exported from `XyChart.tsx`, so existing imports keep working) and `VolumeHistogram` uses it for the y-axis ticks. Tooltips keep their existing compact format.
