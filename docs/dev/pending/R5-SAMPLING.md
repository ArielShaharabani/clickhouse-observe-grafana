# R5-SAMPLING pending notes

**This change adds new SQL paths** (new `src/sql/fullScan.ts`; additions to `src/sql/fieldStats.ts` and `src/sql/kql/_values.ts`). The coordinator should run the security review. (1) `buildPrefixValuesQuery`: `SELECT toString(<expr>) AS value, count() AS count FROM <db>.<table> WHERE <buildWhereConditions: time + other filters> AND value ILIKE '<prefix>%' AND value NOT IN ('{}','[]','null') GROUP BY value ORDER BY count DESC LIMIT 20`. The prefix is user text. It reaches SQL only through `escapeLike` + `quoteString`, so `%`, `_`, `\` and `'` match literally (jest covers this). `<expr>` must pass `isSafeColumnExpr` or be a single quoted identifier, otherwise no query runs. That check matters because the KQL bar hands an undiscovered field name over verbatim (see Deferred). (2) `buildFieldStatsFullScanQuery`: the sampled batch's shape without `ORDER BY … LIMIT 5000`, using bounded aggregates (`countIf`, `uniqIf`, `topKIf(10, 1000, 'counts')`, `minIf`/`maxIf`, `quantileIf(0.5)`, `histogramIf(20)`). It deliberately avoids `sumMap`/`groupArray`, which are unbounded over millions of rows. Field expressions come from field discovery, as before, with positional aliases. (3) `buildRowEstimateQuery`: `EXPLAIN ESTIMATE SELECT 1 FROM … WHERE <same conditions>`, which reads no data. All three end in one SETTINGS clause via `withSettings`. The budgeted ones use `budgetSettingsFragments`, which puts the budget before and after the view's fragments, so a view's `extraQuerySettings` can't lift `max_execution_time` / `max_rows_to_read` or turn `'break'` into `'throw'`. The wall clock is also capped at the view's `queryTimeoutSeconds`. These queries contain `'break'` overflow modes on purpose, so the Diagnostics Warnings tab (`checkSqlIntegrity`) flags them as `overflowBreak`. The results are labelled in the UI instead.

## CHANGELOG

### Added
- **Rare values in value autocomplete.** After 2+ characters of a value in the KQL bar or the filter editor's value box, Observe also looks the prefix up over the whole time range (budgeted to 2 s and 20M rows read). Matches come first with their full-range counts, then the sampled values.
- **Scan full range** in the field popover (Top values and Distribution) and on the Field statistics tab. It reruns the statistics over every matching document instead of the 5,000 newest (budgeted to 10 s and 20M rows read). The caption says whether the scan was complete, partial (hit the row-read limit, with the estimated total), unknown, or cut off by the time limit. Counts are marked approximate when they are estimates.

## Decision

User item 15, with both approved changes implemented. Measured on CH 26.3 against `perf_logs_50m`: with `timeout_overflow_mode = 'break'`, an aggregate returns **zero rows** when the time limit fires, with or without GROUP BY. Only `read_overflow_mode = 'break'` returns a partial aggregate. Consequences:
- Autocomplete uses the approved budget (2 s / 20M, both `'break'`). A timed-out lookup returns nothing and only the sampled list shows. On this host a Map-value prefix over all 50M rows took 2–3 s and so returned nothing (`ServiceName` LowCardinality: 1.2 s, found). On a warmer or faster server, or a shorter range, it finds values.
- Stats scan: an explicit click, so its wall clock is **10 s** instead of 2 s. On the perf fixture, reading one Map value column for 20M rows alone takes about 4 s, and a time-limit hit gives no result at all. The row cap stays at 20M. Completeness is decided like this: no row back means the time limit was hit. `scanned ≥ cap`, or an `EXPLAIN ESTIMATE` above the cap, means partial (rows). An estimate within the cap means complete. If the estimate is unavailable (for example, if the Grafana datasource refuses `EXPLAIN`, which I couldn't check without Grafana access), the caption says "completeness unknown". There is no X-ClickHouse-Summary path: the Grafana ClickHouse datasource doesn't expose rows_read in frame meta.
- Exact-but-unbounded aggregates were replaced: top-value counts come from `topK(…, 'counts')`. They are exact while a field has ≤ 10,000 distinct values, and the field is flagged approximate otherwise (or when topK reports an error, or distinct ≥ 65,536 for `uniq`). Numeric distribution: `histogram(20)` re-binned client side into 10 equal-width buckets (approximate). For discrete integers this spreads counts across neighbouring buckets.
- Merge order: full-range matches first (true counts), then sampled-only values. Minimum prefix length is 2 (the brief allowed 1–2), which is lighter on DB load. A KQL wildcard prefix (`pay*`) doesn't trigger a lookup. The prefix lookup reuses the value cache (120 s TTL, key = sampled key with `prefix=<lowercased>`), so `clearValuesCacheForTable` clears it too. Debounce: the KQL bar's existing 250 ms, plus a new 250 ms one on the filter editor's value input.
- Tab scope: the button profiles the current page of fields (≤ 25) and stays on across pages until `Back to sample` or a scope change. It is not persisted in the URL.

## Deferred

- Pre-existing, not changed: `suggest.ts` `fieldSqlExpr` falls back to the raw typed field name as the SQL expression for the **sampled** value lookup (`toString(<typed text>)`). The new prefix path refuses such expressions. The sampled path should get the same `isSafeColumnExpr` guard, but that is left to the r5-json agent, who is editing that code.
- The lens/ContextView filter editors get the prefix lookup automatically through the shared service. Lens field pickers don't (they don't list values).
- Real `rows_read` from ClickHouse (X-ClickHouse-Summary) would replace the EXPLAIN-based estimate. It needs datasource support.
- A smarter time budget for the stats scan (a progressive/sliced scan that keeps partial results when the time limit is hit).
